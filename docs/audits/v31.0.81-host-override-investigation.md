## Confirmed cause

Actual staging direct fallback DYE-682947: host entered T3 hole 1 gross 6;
assigned remote later saved 8. Host retained 6 after two sync attempts, remote
retained 8; host diagnostics showed zero pending, two parity conflicts, successful
network phases and transport direct/PGRST202. Accepted DYE-119214 untouched.

applyTeamGrossScore records sharedHostScoreOverrides for both partners when the
host changes a remote-assigned team's score. shouldAcceptRemoteSharedPlayerHoleEntry
unconditionally returns false for a host override key. The merge returns before
resolveSharedScoreWrite can compare authority, values or timestamps.
acknowledgeSharedScoreOperations removes acknowledged outbox records but does
not retire override keys. No retirement path exists in the current source.
Thus an acknowledged historical takeover acts as a permanent receive prohibition.

Disposable live-engine probe ran this sequence separately with direct and rpc
transport markers: host gross 6, two queued operations, both acknowledged, zero
pending, remote pair gross 8 with newer timestamp. Both runs retain 6 with two
override flags. Removing only those flags in the disposable fixture makes the
same merge accept both 8s. Probe is ignored under tmp/report-qa/shared-staging/
investigate-host-override.mjs; no real browser or saved round was patched.

This is shared client merge logic, so the problem is not limited to RPC absence.
The RPC-mode isolated reproduction is not an actual hosted RPC service retest.
Existing focused suites pass 14/14, zero skips, demonstrating the missing coverage:
they protect host overrides and reject stale/unauthorized writes, but do not test
the post-acknowledgement hand-back sequence. Network/auth/schema errors do not
explain this reproduced failure. Server completion protection is not implicated.

## Proposed narrow behavior change — owner review before implementation

Treat takeover protection as protection for an outstanding host edit, rather than
permanent ownership of a player/hole assigned to another scorer.

1. Retain protection while the corresponding host write is pending or not durably
   reconciled. Acknowledgement of an older operation must not release protection
   for a newer local edit, nor may a storage failure release it.
2. Retire active protection only against the acknowledged current edit and verified
   canonical server state. Keep any needed historical takeover evidence separately
   from the active receive gate. Acknowledge alone is not proof of card parity.
3. Once released, use existing authorized-source and stale-write checks for later
   cloud changes. A later valid assigned scorer correction may update both partners.
   Older rows, explicit wrong participants and still-pending host edits stay protected.
4. Handle pre-fix flags on unfinished rounds conservatively: reconcile against
   pending operations and canonical cloud rows; do not wipe all flags on load or
   reset the match. Preserve completed/frozen records and settlements entirely.
5. Apply identical lifecycle rules to direct and RPC transports. No server migration,
   scoring/net/payout change, finalization bypass or new user-facing mode proposed.

Material policy implication: a deliberate host correction will no longer block
every future assigned-scorer correction forever. If permanent host-only control is
desired, it must be represented by an explicit assignment/control decision rather
than an invisible historical flag. Confirm this behavior before implementing.
